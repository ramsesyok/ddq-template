### M-08（Medium）番号なし付録の後に続く付録で、HTMLの表番号と参照が一つずれる

実測。対象は `cli/src/commands/tag.rs:123–151` と `cli/src/replace.rs:68–82`。全ファイルの事前照合と、各ファイルの確定の間に時間差がある。Windowsで一時原稿を読み書き共有・削除非共有で開き、`tag apply --all` が一時ファイルを用意した後に別ハンドルから一行追記した。フラッシュして同じハンドルから追記を読み戻し、閉じると、ddqは終了コード0・ラベル1件を報告した。最終内容はラベル付きの元見出しだけだった。PR #143のZIPから取り出したリリースビルドでも、保存直後に追記あり、終了0、終了後に追記なしを再現した。短い共有ロックを待ち直して **rename が成功する経路** でも起きるため、承認済みの直接書き込み例外を廃止するだけでは解消しない。各対象の元バイトを確定処理まで渡し、書き手の排他と再照合を組み合わせる。競合を安全に判定できない共有状態では止め、既に書いた対象を報告する。複数ファイルの後続対象、`rev diff --write` の読後照合（`cli/src/commands/rev.rs:262–270`）も同じ条件で確認する。

**C-02　一時ファイルの書き込み・同期失敗でも、元ファイルを切り詰めて書き直す（リリース準備前に要修正）。**

静的。 `cli/src/replace.rs:24–39,51–62,71–82`。 `swap_in` は一時ファイルの作成、`write_all`、`sync_all`、rename の失敗を同じ結果で返し、呼び側はすべてに `fs::write` を試す。例えば、旧内容を解放しても新本文を収容できない空き容量で書き込みが失敗すると、二度目は元ファイルを切り詰めた後で再び失敗しうる。原稿、改訂YAML、機構ファイルが対象。実ディスクを満杯にする試験は行っていない。承認記録は、Windowsで付け替えを拒まれて待っても解放されない場合の互換動作を扱う（`docs/refactoring-progress.md:448`）。作成・書き込み・同期のエラーは原本に触れる前に返し、互換動作に進めるエラーを最終renameの共有違反に限定する。障害注入で元ファイルのハッシュとエラー種別を検証する。

**C-03　下書きへの添付が一部失敗しても、マニュアルの次行で不完全なReleaseを公開しうる（公開前に要修正）。**

静的。 `docs/manual/chapters/18-maintainer/06-release.qmd:121–131`。新しい版に置き換えてBash例をまとめて実行する場合、チェックサム、下書き作成・アップロード、公開が独立したコマンドで、失敗時に停止する指定がない。コメントは資産を確かめるよう指示するが、リモートの資産を確認するコマンドも公開前の停止点もない。使用環境のGitHub CLI 2.92.0は、明示的な `--draft` で作成後に資産アップロードが失敗するとエラーを返し、その下書きを残す。片方だけ添付された後に通信が回復すれば、続く `gh release edit … --draft=false` がそれを公開しうる。これは保守者の書き込み権限を使う現行手順の問題で、CI自体は読み取り専用。実際のReleaseの作成や障害注入は行っていない。各段階の失敗で停止し、特定した下書きの実資産名2件・状態・digestがそのrunの一覧と一致したときに限り公開する。失敗した下書きからの再開は、模擬応答で「片方のアップロード失敗後に公開呼び出しがゼロ」を確認する。[GitHub CLI 2.92.0の作成・失敗処理](https://github.com/cli/cli/blob/v2.92.0/pkg/cmd/release/create/create.go#L460-L519)

## 5. アーキテクチャ・互換性

**CLIと拡張の境界。** Rustが原稿走査、ラベル提案、Git差分、文書発行、版の適合判定を所有する。拡張は設定→同梱→PATHでexeを選び、引数列で起動する。JSONの形を確認し、終了コード3のときだけ機構の不一致として扱う。他の実行エラーと診断は別に表示する（`cli/src/main.rs:240–255`、`E/src/ddq/locate.ts:23–46`、`run.ts:60–109,149–166`）。CLI単独の `init/add/update/setup/pdf/html/diagrams/tag/rev` はVS Codeに依存しない。HTML出力先など一部の案内は文字列契約で、変更時は共有fixtureの同時検証が必要。RustとReactの間で文書モデルを全面共通化する利点は認めなかった。

**Rust内部。** `commands/` から `doc/`、埋込資産、Quarto、図のエンジンへ依存する。走査の入力は借用し、呼び元へ返す本文と編集計画は所有する。旧版メモの引き継ぎ等のcloneには寿命を分ける理由がある。走査の二重化を減らした一方、編集計画と原本の一致を確定する責務は残った。Windowsではコードページに入らない文字と長いパスを事前診断し、日本語・空白も実生成で確認した（`writing_folder.rs:29–105`）。起動時の失敗は文脈付きエラー、ブラウザとJVMはタイムアウトやkill・wait、WindowsのJob Objectを持つ。不正入力、循環include、欠損ファイル、外部コマンド失敗はそれぞれ警告・エラーの契約がある。Unixでの置換・権限は今回実機で確認していない。

**分離後の依存。** 配布用mainにreleaseのdispatchはなく、`zip_archive` は `cli/src/bin/ddq-release/main.rs:10–16` から使う。Cargoパッケージの通常依存に `zip` が残るのは保守者用exeがZIP作成・VSIX読取を行うため。共有の `quarto.rs`、`tempfile`、ハッシュ、探索処理には利用者用の呼び元もある。Cargoパッケージ単位のコンパイル依存と製品exeの機能は異なる。未使用コードを根拠に別crateへの全面移設を求める状況ではない。

**拡張とWebview。** 起動・終了は `E/src/extension.ts`、プロセスの生存管理とUTF-8ストリームは `ddq/run.ts`。フォルダ単位の排他、設定の再読込、workspace変更時の世代照合、パネル破棄時の購読・タイマー解除がある。`tableEditor/activateTableEditor.ts:116–120,168–232` は文書版、セッション、確認ダイアログの前後を検査する。表はテキストエディタに対するパネル、改訂YAMLはCustomTextEditorProviderであり、いずれもWorkspaceEditを使う。保存・Undo/Redoの主体をVS Codeに置く設計は妥当。改訂画面だけは全置換とメッセージの順序が保証を崩す（H-02ほか）。Reactの型はメッセージの実行時検証を代替しない。`package.json:25–28` の非信頼workspace無効化、Webviewのnonce、バンドル限定の `localResourceRoots`、外部接続を許さないCSPを確認した。ユーザーが信頼したworkspaceの設定やQuartoフィルタは実行対象になる。VSIXスモークは信頼制限を無効化して起動するため、非信頼時の動的実証には数えない。

**文書生成。** Quartoがbookとincludeを解決し、Luaが図と表を変換、TypstがPDFを組版する。HTMLはQuartoの採番後、JSが全章の番号を集めてから他章参照を引き直す。RustにはQuartoなしでtag/revを行う走査と、Mermaid／PlantUMLを先に描く経路がある。キャッシュキーと結合表の共有fixture、PDFのページ別検査、HTML番号・再実行の試験はこの分担に合っている。実装者記録では通常サンプルの版間比較141項目が一致。実測の標準雛形はHTML 8ページ。H-01のように各実装が同じ要素を落とすと相互一致の試験だけでは検出しにくい。版上げ時は行末コメントを持つ既存文書で走査対象が増えること、新たな候補や番号が出ることを変更履歴へ記す。

**障害と再実行。** buildの `candidate` は1日保持。verify-zipとverify-vsixは同じ実行から取得し、どちらかが失敗すれば `publishable` は起動しない。最後のランナーでもチェックサムを再確認する。失敗回が前の公開資産を置き換えるジョブや公開用秘密情報は見当たらず、リポジトリ権限は `contents: read`。同じrefの同時実行は `concurrency` で制御するが、版名は一意キーではなく、別の実行に同じ名の成果物を作れる。一般の下書き作成後のアップロード失敗は保守者が下書きと実行IDを照合して回復する。公開済み資産を自動で戻す必要はない。途中ジョブだけの再実行、下書き途中での中断を今回は実施していない。

**供給経路。** Cargo.lock、package-lock、Quartoの版、PlantUML jarのSHAを固定。キャッシュヒット後もjarを照合し、梱包は `npm ci`。RustキャッシュとVS Codeキャッシュは用途が異なり、後者はバージョンを完全には固定しない。通常CIの `ci.yml` に明示的な `permissions` はなくリポジトリ既定に依存する。配布workflowの読み取り権限から通常CIの実効権限までは断定できない。タグ参照の外部Actionが差し替われば、読み取り権限でも候補に入るファイルを生成時に変更しうる。同じ実行が生成するSHA一覧は独立した真正性の証明にはならない。再現性を含めL-02に記した。

## 10. リリース判断と残る検証

**どの変更に起因するか。** タグ付き改訂の最初の本文をタグ照会より先に表示するM-01は、比較元と処理順が逆になった回帰である。C-03も、旧手順の単一の `gh release create` を、明示的な下書き作成と独立した公開コマンドに分けた際に生じた。C-01・C-02は、元から直接書き込みをしていた実装に保護を加えたものの、その保証から漏れる経路。H-01の部の認識、H-02の全置換、M-02の保存戻り値の扱い、M-03の列挙失敗は比較元にも同じ構造がある。出荷判断では現在の影響を評価し、修正時の原因切り分けにはこの違いを使う。

1. **原稿保全を先に直す。** C-01は通常の保存とラベル付けが同時に起きるだけで成立する。短い共有ロックの解放前後、複数原稿の後続ファイル、新規・既存の改訂YAMLについて、競合時の終了値・原本ハッシュ・部分成功表示を確認する。C-02では一時作成・書き込み・同期・最終renameを別々に失敗させ、元ファイルが完全であることを検査する。
2. **文書と編集画面の正解を外側から検証する。** ファイルを持つ部の本文にラベル・図表・他章参照を置き、Quarto入力、CLI順序・改訂差分、PDFとHTMLの番号を照合する。改訂画面では二つの編集、Undo/Redo、遅い初回タグ照会、保存拒否を組み合わせ、無関係なメモと確定済み表示が保たれることを確認する。
3. **正式候補を新しい版で作る条件を整える。** 修正後にテンプレート・拡張・lockfileの版を揃え、既存文書の明示update、章順・ラベル・表・BOM・履歴の利用者向け変更点を記録する。下書きへの片側アップロード失敗で公開を止める処理を確認する。対象main SHAで通常CIと候補を照合し、タグの実SHA、ZIP／VSIX両方のdigest、通知を確認できた一式だけを下書き公開の対象とする。
4. **配布先の受入を残す。** OSで外部通信を遮断し、Node/npmなし、ローカルJava＋jar・LANサーバ・PlantUMLなしを分けて実行する。日本語IME、セル結合、未保存の画面切替、異版CLIからの案内、旧2拡張からの移行は実操作で確認する。今回のWindowsでの自動試験、静的CSP検査、ローカルJVM成功からこれらの合格は導けない。

残す技術的負債は、Rust/JSの限定的なYAML解釈、Rust/Lua/TSの図・表の境界、手元の配布物を入れ替える途中で失敗した場合の復元、ツールチェーン・書体の環境差である。まず今回の具体例を回帰試験に加えるほうが、CLIの全面再分割や描画系の統合より改善効果を確かめやすい。
