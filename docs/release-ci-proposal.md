# 配布を GitHub Actions に移す案（REL-02・CI-01 の残り）

2026-11-22 作成・**承認**（§2 はすべて推奨どおり。§2 の 4 の通常 VSIX の artifact は残す）。`docs/refactoring-plan.md` §7 に追記した。
実施の記録は `docs/refactoring-progress.md`、現行の手順は利用マニュアル 18 章と `cli/DESIGN.md` §7.5・§7.6。

## 1. 要点

- **Actions に移すもの**: 配布候補の作成と検査。1 回の実行で ZIP と VSIX を作り、別の新しいランナーで検査する。
  すべての検査に通った回だけ、公開に使う成果物を残す
- **保守者に残すもの**: 公開とタグ（計画の CI-01「公開・タグ作成は保守者の操作」と、§7「自動公開は含めない」のとおり）。
  成果物をダウンロードしてハッシュを照合し、下書きのリリースに載せてから公開する
- **梱包の中身**: 今の `ddq release` を CI から呼ぶ（推奨）。版の照合（REL-03）、ライセンス表示の照合（REL-01）、
  ZIP の UTF-8 名フラグと読み直しの照合は、試験済みのものをそのまま使う。製品の exe から外すかは別に決める（§5）
- **これで閉じる項目**: CI-01 の残りと REL-02。REL-02 の保証の範囲は「公開に使えるのは、すべての検査に通った 1 回の
  実行の成果物だけ」にする

## 3. 推奨案の流れ

新しい workflow `.github/workflows/release-candidate.yml` を作る。

| ジョブ | ランナー | すること | 次に渡すもの |
|---|---|---|---|
| `build` | Windows | `cargo build --release --locked` で ddq.exe を作り、その exe で `ddq release <出力先>` を実行する（マニュアルの update → pdf → html、拡張の `npm ci` と同梱版 VSIX の梱包、ZIP の作成と読み直し）。ZIP・VSIX の SHA-256 と、使った Quarto・Node・Edge の版を書いた一覧を作る | `candidate`（ZIP・VSIX・一覧。保存は 1 日） |
| `verify-zip` | Windows | ZIP を照合する（名前・日本語名の UTF-8 名フラグ・CRC・ライセンス表示・manual があること・jar が無いこと）。取り出した exe で `init --no-render` → `pdf` → `html` を通す | — |
| `verify-vsix` | Windows | 同じ VSIX で `npm run test:smoke -- <VSIX>`。VSIX の中の exe とライセンス表示が、ZIP の中のものと同じこと | — |
| `publishable` | Linux | 上の 3 つがすべて通ったら、一覧のハッシュを照合し、`release-<版>` として保存する | `release-<版>`（保存は既定の 90 日） |

- `permissions: contents: read`。CI は公開済みのリリースにも、タグにも書き込まない
- `concurrency` で、同じブランチの実行は 1 つずつにする
- Quarto 1.9.38、Node 22、Cargo は `--locked`（今の CI と同じ）
- 起動対象のパスには、配布物に入るもの（`cli/`・`template/`・`extensions/ddq-template/`・`docs/manual/`・`README.md`・
  `AGENT-GUIDE.md`・`LICENSE`・`THIRD-PARTY-NOTICES.md`）と workflow 自身を含める
- 照合の処理は、統合の検証で使ったものを `cli/tools/check_release.py`（新設）としてリポジトリに入れる。CI と手元の両方で、
  `ddq release` の出力先に対して同じものを流せる
- `--with-sample` は手動実行の入力で選べるようにする（既定は付けない）

以下は提案時の手順。現行の公開手順は[利用マニュアル「リリースを配る」](manual/chapters/18-maintainer/06-release.qmd#sec-release-publish)にある。

```bash
# main の、すべてのジョブが通った実行から取る
gh run download <実行の番号> -n release-<版> -D release
# 一覧の SHA-256 を照合してから、下書きで作り、資産がそろったのを見てから公開する
gh release create v<版> release/quarto-template-<版>.zip release/ddq-template-win32-x64-<版>.vsix \
  --draft --target <その実行のコミット> --title "…" --notes-file <リリースノート>
gh release edit v<版> --draft=false
```

> 2026-11-23 追記: 下書きを作るコマンドと公開するコマンドを分けると、片方の資産だけ上がった下書きを次のコマンドが
> 公開しうる（レビュー `docs/refactoring-review.md` の C-03）。マニュアル 18 章「リリースを配る」の手順は、`--draft` を
> 付けない 1 つの `gh release create`（gh が下書きで資産を上げ、2 つとも上がったときだけ公開し、失敗したら下書きを消す）に
> 戻し、既にあるタグの指すコミットの照合と `--prerelease` を足した（M-05）。同じ日、選んだ実行と同じコミットの
> `ci.yml`・`extension.yml` が通ったかの照合も足した（M-04。配布候補は専用の検査だけで残るため）。配布候補の workflow は
> 外部の Action をコミットの SHA で固定し、Rust・書体の版・スモークの VSCode の版も記録し（L-02）、同じ枝への要求を待機開始順に
> 最大100件まで待たせる（`queue: max`。満杯時の追加要求は取り消される）。マニュアルでは取得のたびに新しい一時フォルダを使い、
> CI 待ちの後も、手元の試作物がある場合も同じ手順で再実行できる。

`release/` の下のファイル名は今と同じなので、今の手順の `gh release create` の行はそのまま使える。
タグは実行のコミットを指すので、タグと配布物のコミットが必ず一致する（今は「マージ後の main から作り直してからタグを打つ」を
保守者が守る必要がある）。

## 5. ddq.exe から `ddq release` を外すか（別の判断）

`ddq release` は保守者だけが使い、テンプレートのリポジトリが無いと動かないので、発行者に配る ddq.exe に入っている意味は無い。
ただ、外すと次が変わる。

- 保守者が使うコマンドが変わる（マニュアル 18 章、`cli/DESIGN.md` §2 の決定 1、`tests/release.rs` 17 件）
- 外した処理の置き場所が要る。たとえば同じ `cli/` のワークスペースに保守者用の別のバイナリを作り、ZIP の作成などのコードを共有する

この案（§3）は `ddq release` をそのまま呼ぶので、外すかどうかに左右されない。**CI の流れが安定してから、別の項目として決める**ことを勧める。

**決定（2026-11-23、保守者）**: 外した。処理は同じ `cli/` パッケージの保守者用の別の exe `ddq-release`（`cli/src/bin/ddq-release/`）に移し、
配る ddq.exe を `--ddq` で受け取る（既定は ddq-release と同じフォルダの `ddq.exe`）。利用マニュアルもその ddq.exe で作る。
CI（`release-candidate.yml`）は `ddq-release.exe … --ddq cli/target/release/ddq.exe` を呼ぶ。実装仕様書（`docs/cli-impl`・`docs/ddq-template-impl`）は
この分離の分だけを直した。記録は `docs/refactoring-progress.md`。

## 6. 先に確かめること・リスク

- **フォント**: 手元で作ったマニュアルの PDF には Meiryo UI と BIZ UDGothic が埋め込まれている（`template/lib.typ` の
  `JP-SANS`・`MONO` の最初の候補）。GitHub のランナーにこの 2 つがあるかは確かめていない。無ければ別の書体に落ちて紙面が変わる。
  試走で、埋め込まれたフォントを手元の PDF と比べる。無ければ、日本語の追加フォントを入れる手順を `build` に足す（数分かかる見込み）
- **mermaid の図**: ランナーの Edge は、日本語の代わりのフォントが手元と違う（ci.yml の冒頭の、golden の許容差の注記）。
  マニュアルの mermaid の図 4 枚が、手元と違う配置になりうる。試走で比べ、違えば内蔵の merman で描く（`DDQ_MERMAID_ENGINE`。`cli/DESIGN.md` §2 の決定 4）か、差を受け入れるかを決める
- **ランナーの更新**: 同じコミットでも、ランナーのイメージが更新されると Edge などの版が変わる。使った版を一覧に残す
- **日本語のパス**: ランナーは CP1252 で日本語のパスを作れない（ci.yml の注記）。日本語のパスでの確認は手元に残す
  （ZIP の中の日本語名は Rust が扱うので、ランナーでも作れる。`tests/release.rs` が CI で通っている）
- **所要時間**: 測っていない。参考に、今の CI の `cli` は 9〜20 分、実ホストは 7〜11 分だった。試走で測り、§2 の 3 を決める
- **最初の試走**: `workflow_dispatch` は、workflow が既定のブランチ（main）に入るまで手動で起動できない。workflow を入れる PR では、
  workflow 自身を変えたときだけ PR でも走るようにして試走する
- **保存期間**: artifact は 90 日で消える。公開したリリースの資産が正の記録になる
