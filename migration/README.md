## 基本の考え方 — 3つの層に分ける

「Word を Quarto に変換する」と一括りにすると判断を誤る。文書は性質の違う
3つの層でできており、**層ごとに最良の入力元が違う**。

### 層 A — 文章・表

**最良の入力元: 原本（`.docx` / `.pptx`）**

本文・箇条書き・表。機械変換が効く唯一の層で、移行作業の大半はここが自動で片付く。

### 層 B — 図

**最良の入力元: 提出用 PDF**

構成図・フローチャート・IPO 図。原本からは「形」が取り出せず、PDF からは
ベクターのまま取れる。**唯一 PDF が原本に勝つ層**である。

### 層 C — 採番・相互参照・章立て

**入力元によらず、人が作り直す**

既存文書の「図 3.2-1」は、原本の中でもただの文字列である。テンプレートの
`{#fig-x}` と `@fig-x` への載せ替えは自動化できない。**移行コストの本体はここ**であり、
どの入力を選んでも同じだけかかる。「PDF から変換すれば楽になるのでは」という
期待が外れるのはこのためである。

逆に、ここを通しさえすれば、以後の改訂で図表番号がずれる事故は消える。

## パターン別のおすすめ変換方法

| 原本のパターン | 層 A　文章・表 | 層 B　図 | 層 C　構造 |
|---|---|---|---|
| **1　Word のみ** | `.docx` を pandoc で変換。見出しを解析して章フォルダへ分割する | Word 内の図形は変換で消える。提出 PDF があれば該当ページから SVG、無ければ Word 上で「図として保存」 | 見出しの手番号を削り、図表番号を `label=` と `@fig-x` に載せ替える |
| **1′　Word が複数ファイル** | `.docx` を**ファイルごとに**変換。展開先を必ず分ける（罠を参照） | 同上 | **分割済みなので有利**。ファイルと章フォルダがほぼ 1 対 1 で対応する |
| **2　PowerPoint のみ** | `.pptx` を python-pptx で抽出（pandoc でも読めるがノートが落ちる） | **提出 PDF** からページ単位でベクター SVG 化。PowerPoint も LibreOffice も要らない | **章立てを設計し直す**。スライド順をそのまま章にしても文書にならない |
| **3　Word ＋ PowerPoint** | 本文は `.docx` から。PPT 側の文字は補助的に `.pptx` から | **提出 PDF** の PPT 由来ページから SVG。**IPO だけは `.ipo` に作り直す** | Word 本文の「別紙参照」が `@tbl-x` になり、リンクとして機能するようになる |

提出用 PDF は、どのパターンでも**正解表**として使う。何がどの順で提出されたかの
確定情報であり、ページ数を突き合わせれば「原本の存在しない別紙」も見つかる。

### 複数ファイルの原本は不利ではない

このテンプレートは**章＝フォルダ**が規約である（利用マニュアル4章）。したがって
章ごとに分かれた `.docx` は、すでに人間が意味のある単位で切ってくれている状態であり、
移行にとって有利に働く。

| 原本の形 | 必要な作業 |
|---|---|
| 章ごとに分かれた docx | `第3章.docx` → `chapters/03-xxx/index.qmd` へほぼ 1 対 1 で流し込む |
| 1本にまとまった docx | 見出しを解析して**分割する処理が要る** |
| 結合済み PDF | 分割に加えて、章境界をページ上の見た目から推定することになる |

ファイル単位で変換できるため、1章だけパイロットを回す・原本が改訂されたら
その章だけ再変換する・章ごとに担当を割り振る、といった進め方がそのまま取れる。

また Word の相互参照（REF フィールド）は**ファイルをまたぐと機能しない**ため、
複数ファイル構成の原本では「第3章参照」が最初から手打ち文字列になっているのが普通である。
つまり多ファイル原本ほど、テンプレートの `@sec-x` / `@tbl-x` に載せ替える価値が大きい。

## 入力元ごとに何が残り、何が落ちるか

| 要素 | `.docx` | `.pptx` | 提出 PDF | 補足 |
|---|:---:|:---:|:---:|---|
| 見出し階層 | △ | △ | ✕ | docx は**見出しスタイル使用時のみ**。直接書式（太字＋サイズ）だと全部平坦な段落になる。PDF はフォントサイズから推測するしかない |
| 段落・箇条書き | ○ | △ | △ | pptx は図形単位の文字が z-order 順に平坦化され、階層が消える（実測） |
| 表 | ○ | ○ | ✕ | PDF は素抽出だと 4列×4行がバラバラの16行に崩壊。座標検出を掛ければ罫線ありの表は復元できる（実測） |
| 結合セル | ○ | △ | ✕ | **docx は縦結合・横結合ともグリッド表の結合として保存される**（実測） |
| 画像 | ○ | ○ | ○ | `--extract-media` で取り出せる |
| 図形・矢印・配置 | ✕ | ✕ | ○ | **この1行が PDF を使う理由**。pptx はひし形の判断記号も矢印の向きも失われ、文字だけが残る（実測） |
| 発表者ノート | — | △ | ✕ | pandoc は落とす。python-pptx なら取れる（実測） |
| 数式 | ○ | — | ✕ | docx の数式は LaTeX 記法に変換される |
| 枠・資料番号のノイズ | 無 | 無 | **有** | PDF は `SD-2026-001` `26 / 48` が毎ページ本文に混入し、図中の軸ラベルまで本文に流れ込む（実測） |

### 実測の内訳

**pptx の図形は文字しか残らない。** 四角＋ひし形＋コネクタで作った IPO 風スライドを
pandoc の pptx リーダに掛けると、こうなる。

```
入力 / ・受注入力画面 / ・顧客マスタ / 処理 / 1. 入力値を検証 / … / 在庫あり?
```

「在庫あり?」がひし形（判断）だったことも、矢印がどこへ向いていたかも残らない。
pandoc の pptx リーダは作図変換器ではなく、**文字起こしの手間を省く道具**である。

**PDF は表が崩壊する。** `docs/design-doc.pdf` p.26 の 4列×4行の表を素直に抽出すると、
セルが1行ずつバラバラの16行になり、行と列の境界が消える。

座標ベースの表検出（PyMuPDF `find_tables`）を掛けると本物の表は 5行×4列で正しく
復元できたが、**同時に外枠を表と誤検出**し、ページ本文まるごとを1セルに飲み込んだ
偽の表も出した。

**PDF は図中の文字が本文に混入する。** グラフの軸ラベルが表とキャプションの間に流れ込む。

```
…会計連携 バッチ時間 10分 30分以内
20件/分  2.4  2.2  2  1.8 … 応答時間 (秒)      ← グラフの軸ラベル
図 7.1-1　負荷段階別の応答時間
```

PowerPoint 由来の PDF はページの中身がほぼ全部「図の中の文字」なので、この混入が全編で起きる。

**PDF の図はベクターのまま取れる。** ページを SVG に出した結果:

| 方式 | サイズ | 中身 |
|---|---|---|
| `text_as_path=False` | 46 KB | path 42・**text 199（本物の文字）** |
| `text_as_path=True` | 325 KB | path 228・text 0（文字も輪郭化） |

横向きページは 12.5 KB。ラスタライズは一切起きていない（`<image>` 0個）。
`text_as_path=False` は軽くて文字検索も効くが、**フォントが手元に無いと字形がずれる**。
配布先のフォント環境が読めないときは `True`（自己完結・7倍重い）を選ぶ。

## 図は貼るか、作り直すか

PDF から SVG が安く取れるようになると、すべて貼り付けて済ませたくなる。
しかし貼り付けた図は**テンプレートの機構の外側**に出るため、図の種類で線を引く。

| 元の図 | 移行先 | 理由 |
|---|---|---|
| IPO 図 | **作り直す** `::: {.ipo}` | 自動採番・`@tbl-x` 参照・横向き定型ページ・「（1／2）」分割がすべて効く。画像で貼ると全部死ぬ |
| フローチャート・状態遷移図 | **作り直す** mermaid | 原稿の差分としてレビューできるようになる。様式も揃う |
| 複雑な構成図・ネットワーク図 | **貼る** PDF → SVG | 作り直しが高くつき、得るものが少ない。割り切ってよい |
| 写真・スクリーンショット | **貼る** 原本から抽出 | そもそも作り直せない |

## 踏むと痛い罠

### 複数の docx を同じ展開先に変換すると、画像が無言で上書きされる

pandoc は画像を docx 内部の関係 ID（`rId9`）で命名するため、文書が違えば必ず衝突する。
第1章の構成図が第5章の図に化けても**警告は一切出ない**（実測）。

```
media/media/rId9.png   ← 112バイト（第5章の画像だけが残った）
```

展開先をファイルごとに分けること。

```bash
quarto pandoc -f docx -t markdown --extract-media=diagrams/ch01 第1章.docx -o ch01.md
```

### PDF の表検出は、ページの外枠を「表」と誤検出する

本文まるごとを1セルに飲み込んだ偽の表が出る（実測）。検出結果はサイズや列数で必ず選別する。

### 見出しに手で振った番号はテンプレートと二重になる

`## 1.1 目的` → `## 目的` に削る。章番号・図表番号はテンプレートが自動で振る。

### ファイル間で見出しレベルがずれていることがある

章タイトルを見出し1にしたファイルと見出し2にしたファイルの混在は、
`--shift-heading-level-by=1` で吸収できる（実測）。

### パスに ASCII 以外を使えない

リポジトリ名・執筆フォルダ名・その上位まで英数字に限る。日本語を含むと
mermaid 図のベクター化が失敗する。取り込み時にリネームが要る。

### 画像パスはプロジェクトルート基準で書く

`/diagrams/x.svg` と書く。`../diagrams/` は Windows でパス結合が壊れてビルドに失敗する。

### 原本と提出 PDF の版が食い違っていることがある

提出後に PDF だけ修正されていると、どちらから変換しても間違ったものを移植する。
「提出した PDF が正」という運用なら、内容の正しさでは PDF が原本を上回る。**着手前に確認する。**

## 着手の順序

1. **提出 PDF で正解表を作る** — 章立て・順序・総ページ数を控える
2. **原本をファイル単位で診断する** — 見出しスタイルの使用率・図形数・表数を数え、
   安い章から着手できるよう並べる（`diagnose.py`）
3. **1章だけパイロットを通す** — 層 C の工数はここでしか読めない
4. **実測値をもとに全体計画を引き直す**

### 移行しない判断も検討に値する

400〜1000ページ級で全面移行を先に決めると、層 C の工数を必ず読み違える。
**既存文書は凍結し、改訂分から Quarto に切り替える**選択肢は現実的であり、
パイロットの実測値が出てから決めればよい。

## 支援スクリプトの計画

スクリプト化の価値は「パターン」ではなく「層」で決まる。ただし層の重みが
パターンごとに違うため、結果として**パターン 2・3（PowerPoint が絡むもの）が
最もスクリプトを必要とする**。そこだけ既製ツールが存在しないためである。

| スクリプト | 役割 | 対象パターン | 依存 | 状態 |
|---|---|---|---|---|
| `diagnose.py` | 事前診断 | 全部 | 標準ライブラリのみ | **実装済み** |
| `tbl.py` | `.tbl` 付与・採番の棚卸し・参照の置換 | 1・1′ | 標準ライブラリのみ | **実装済み** |
| `headings.py` | 見出しの手書き番号を削除 | 1・1′ | 標準ライブラリのみ | **実装済み** |
| `split.py` | 章・節へのファイル分割 | 1 | 標準ライブラリのみ | **実装済み** |
| `pdfsvg.py` | PDF → ページ別 SVG | 2・3 | PyMuPDF | **実装済み** |
| `pptxtext.py` | pptx から文字・表・ノートを抽出 | 2・3 | python-pptx | **実装済み** |

`tbl.py` が層 C に効く。当初は「図表番号の棚卸し」を別スクリプトとして数えていたが、
キャプションから番号を拾う時点で対応表ができるため、**本文の参照を `@tbl-x` へ置換する
処理は `.tbl` 付与の副産物として無料で付いてくる**。層 C の作業量を最も削るのはこれである。

### 作らなくてよいもの

| やること | 理由 |
|---|---|
| docx → markdown 変換そのもの | pandoc の1行で済む |
| 複数 docx の一括変換 | `bat` / `sh` のループで足りる。Python にする必要は無い |
| 章フォルダへの分割 | パターン1（単一の巨大ファイル）だけ必要。パターン1′なら原本の分割をそのまま使える |
| IPO の再作成・章立ての設計・図を貼るか作り直すかの判断 | 判断であって、自動化の対象ではない |

## パターン1（Word 1冊）の変換手順

見出し付きの Word 1冊を pandoc に掛けると、**1つの大きな markdown** になる
（pandoc に markdown 出力の分割機能は無い。`--split-level` は epub と chunkedhtml 専用）。
そこから4段階で執筆フォルダの形に持っていく。

### 0. pandoc で markdown にする

```bash
quarto pandoc -f docx -t markdown-simple_tables-multiline_tables \
    --wrap=none --track-changes=accept \
    --extract-media=diagrams/ch01 設計書.docx -o step0.md
```

| オプション | なぜ要るか |
|---|---|
| `-t markdown-simple_tables-multiline_tables` | 既定では罫線を空白で揃えた simple table になり、**テキストから表を検出できない**。パイプ表・グリッド表に固定する |
| `--wrap=none` | 行を折り返させない。折り返されると画像や参照が行をまたいで壊れる |
| `--track-changes=accept` | 変更履歴を反映する（残っていると本文が二重になる） |
| `--extract-media=diagrams/ch01` | **ファイルごとに別のフォルダへ**。同じ展開先だと画像が無言で上書きされる |

### 1〜4. 段ごとに確認しながら進める

```bash
python migration/tbl.py      step0.md -o step1.md --map refs.tsv
python migration/headings.py step1.md                     # まず確認（dry-run）
python migration/headings.py step1.md -o step2.md --apply
python migration/split.py    step2.md -o C:/work/order-design/docs
```

**分割は必ず最後**である。先に分割すると、採番の棚卸しと参照の置換がファイル横断になる。

最後に `_chapters.yml` の中身を `_quarto.yml` の `chapters:` へ貼り、`diagrams/` に画像を置く。

### 番号は元と一致するとは限らない

変換後の番号は**構造から計算し直される**。章を並べ替えれば番号も変わる。
元の Word と一字一句同じ番号になることを期待してはならない。
番号がずれても本文の `@tbl-x` が自動で追従することが、この移行の目的である。

## `tbl.py` — `.tbl` 付与と採番の棚卸し

```bash
python migration/tbl.py step0.md -o step1.md --map refs.tsv
```

やること:

* 表を `::: {.tbl caption="…" label="tbl-1-1-1"}` で囲む（キャプションから番号を除く）
* 図に `{#fig-1-1-1}` を付け、画像パスを `/diagrams/…` に直す
* 本文の「表1.1-1」を `@tbl-1-1-1` に置換する
* 元番号と label の対応表（`--map`）を出す

label は**元番号から機械生成**する（`表1.1-1` → `tbl-1-1-1`）。日本語タイトルを
slug 化しないので、ASCII 制約に触れず、タイトルを直しても ID が変わらない。

`merge-cols` と `widths` は付けない。Word の結合セルはグリッド表の結合として既に
保存されており、手で結合を書いた表に `merge-cols` は効かないためである（利用マニュアル9章）。

実行後、**定義の見つからない参照**と**本文から引かれていない図表**を報告する。
どちらも手で確認する対象である。

## `headings.py` — 見出しの手書き番号を削除

```bash
python migration/headings.py step1.md                      # 確認
python migration/headings.py step1.md -o step2.md --apply  # 適用
```

行頭の数字を機械的に消すと `## 2038年問題` のような正当なタイトルを壊すため、
**番号が見出しの構造と辻褄が合っているときだけ**削除する。

| 見出し | レベル | 番号の階層 | 判定 |
|---|---|---|---|
| `## 1.1 目的` | 2 | 2 | 一致 → 削除 |
| `### 2.1.1 サーバ` | 3 | 3 | 一致 → 削除 |
| `## 2038年問題` | 2 | — | 数字の後に区切りが無い → そもそも対象外 |
| `## 3.11 の教訓`（第2章の下） | 2 | 2 | 上位の番号 2 と繋がらない → **残す** |

既定は dry-run。全件を表示してから `--apply` で適用する。

## `split.py` — 章・節へのファイル分割

```bash
python migration/split.py step2.md -o C:/work/order-design/docs
```

利用マニュアル4章の規約（章＝必ずフォルダ／節・項＝子があればフォルダ／
レベル4以下は分けない）で分割し、`include` を**章フォルダ基準**で書く

## パターン2・3（PowerPoint が絡む）の変換手順

**層 A（文字・表）は原本の .pptx から、層 B（図）は提出用 PDF から取る。**
2つの入力を使い分けるのが要点で、どちらか一方では足りない。

```bash
# 1. どのページが図か調べる
python migration/pdfsvg.py 提出版.pdf --list

# 2. 図のページを SVG で取り出す
python migration/pdfsvg.py 提出版.pdf -o C:/work/order-design/docs/diagrams \
    --exclude-body --md figures.md

# 3. 文字・表・ノートを下書きにする
python migration/pptxtext.py 資料.pptx -o draft.md --media C:/work/order-design/docs/diagrams/ppt
```

そのあと、下書きを章立てに組み直す。**スライド順をそのまま章にしても文書にならない**ので、
ここは人が設計する。

### Word ＋ PowerPoint（パターン3）の場合

## `pdfsvg.py` — PDF から図をベクターで取り出す

```bash
python migration/pdfsvg.py 提出版.pdf --list
python migration/pdfsvg.py 提出版.pdf -o docs/diagrams --landscape --trim --md figures.md
```

`--list` はページごとの用紙サイズ・向き・文字数・描画数を並べ、
**最も多いサイズを本文とみなして**それ以外を図の候補として挙げる。

| 選び方 | オプション |
|---|---|
| ページ番号で指定 | `--pages 9,12-15` |
| 横向きページだけ | `--landscape` |
| 用紙サイズで指定 | `--size 842x595` |
| 本文と判定されたページを除く | `--exclude-body` |

| そのほか | 内容 |
|---|---|
| `--trim` | ページの余白を落とす |
| `--outline-text` | 文字を輪郭化する（フォント非依存になるが 7 倍ほど重い） |
| `--md FILE` | 貼り付け用の markdown を出す。横向きページは `.landscape` で囲まれる |

ラスタライズは起きない。実測では A4 横1ページが 11〜26 KB である。

## `pptxtext.py` — pptx から文字・表・ノートを取り出す

```bash
python migration/pptxtext.py 資料.pptx -o draft.md --media docs/diagrams/ppt
```

pandoc も .pptx を読めるが、**発表者ノートを落とし**、図形の文字を z-order 順に
平坦化する。本スクリプトは読み順（上から下、左から右）で並べ、ノートも残す。

とくに:

* **入力／処理／出力の3欄があるスライドは `::: {.ipo}` の下書きにする。**
  そのまま `module=` と処理名を埋めれば、テンプレートの IPO ページとして採番される
* 図形とコネクタで描かれたスライドには**警告コメントを入れる**。
  枠と矢印は markdown に写らないので、PDF から回収するか作り直す判断が要る
* 実行後、図が主体のスライド番号を集めて `pdfsvg.py --pages` の指定を提示する

### 図はここでは取り出せない

取り出せるのは文字だけである。枠・矢印・配置は失われる。
これは本スクリプトの制限ではなく、**PowerPoint の図を markdown に写せない**という
事実による。図は `pdfsvg.py` で PDF から取るか、mermaid ／ `.ipo` に作り直すこと。

## プログラム詳細設計書

本フォルダのスクリプト6本について、モジュール単位の詳細設計を `docs/` に置いている。
**本テンプレート自身で書かれており**、関数ごとに IPO 図を載せている。

clone した直後は機構ファイル（`design-doc.lua` ほか）が無いので、先に配る。
サンプルの `docs/` と同様、本リポジトリでは機構ファイルを追跡していないためである。

```bash
./template/update-doc.sh migration/docs
```

そのうえで、確認用の HTML（`migration/docs/_book/`）を出す。

```bash
cd migration/docs && quarto render
```

PDF（`migration/docs/design-doc.pdf`）はテンプレート側から出す。mermaid 図が多いため
node と Chrome / Edge が要る。

```bash
./template/build-qmd.sh migration/docs
```

PDF も本リポジトリでは追跡しない（`.gitignore` の方針。サンプルの `docs/` と同じ扱い）。
179 ページ・横向き 49 ページになる。

構成は次のとおり。

| 章 | 内容 |
|---|---|
| 1 概要 | サブプログラム構成、共通プログラム、**起動方法及び使用手順** |
| 2 設計方針 | 設計技法、文書化（本書の凡例）、命名規約 |
| 3 設計条件 | 実行環境・文字コード・変換対象・処理順序・保守の制約と根拠 |
| 4 モジュール仕様 | サブプログラムごとの機能概要・モジュール構造・**モジュール詳細（IPO 図）** |
| 5 局所テーブル仕様 | データクラス5種のデータ項目 |
| 6 メッセージ仕様 | 標準出力・標準エラー出力へのメッセージ |
| 7 メモリ仕様 | なし（Python のため該当しない） |
| 8 設計内容の評価 | 追跡可能性・一貫性・試験と保守の実現可能性 |

> 第4章のモジュール詳細では、処理手順を持つ関数（39 個）に IPO 図を付けている。
> 2〜4行の補助関数は一覧表で機能・引数・戻り値のみを示す。

## `diagnose.py` — 事前診断

原本を1つも変換しないまま、**移行コストの内訳を数字にする**。
OOXML の zip を直接読むので、pandoc も外部ライブラリも要らない。

```bash
python migration/diagnose.py <ファイルまたはフォルダ> [...]
```

```bash
python migration/diagnose.py C:/work/原本 --out shindan.md
```

| オプション | 既定 | 内容 |
|---|---|---|
| `--format {md,csv,json}` | `md` | 出力形式 |
| `--out FILE` | 標準出力 | 出力先（UTF-8） |
| `--no-recurse` | 再帰する | フォルダを再帰的に探さない |

詳しい読み方はスクリプト冒頭の docstring を参照。
